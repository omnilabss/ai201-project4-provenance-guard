# Provenance Guard — Planning Document

## Overview

Provenance Guard is a Flask-based backend service that analyzes submitted text to determine whether it was written by a human or generated by an AI writing tool. The system combines two complementary detection signals — an LLM-based classifier running via the Groq API and a set of stylometric heuristics computed entirely in Python — to produce a confidence score and a human-readable transparency label.

The service is designed to be transparent, contestable, and honest about its own uncertainty. When the system is not confident, it says so explicitly. Authors who disagree with a classification may submit an appeal, which places the submission under human review. All decisions are logged to an immutable SQLite audit trail.

## Architecture

### Submission Flow

```
Client
  │
  │  POST /submit
  │  { text, creator_id }
  ▼
Flask App
  ├─── Signal 1: LLM via Groq API ───────────────────────────────┐
  │      llama-3.3-70b-versatile                                  │
  │      Prompt: "Return JSON {ai_probability, reasoning}"        │
  │      Returns: llm_score (0.0 – 1.0)                          │
  │                                                               │
  ├─── Signal 2: Stylometric Heuristics (pure Python) ───────────┤
  │      - sentence_length_variance                               │
  │      - type_token_ratio                                       │
  │      - punctuation_density                                    │
  │      - avg_sentence_length                                    │
  │      Returns: stylometric_score (0.0 – 1.0)                  │
  │                                                               │
  ▼                                                               │
Confidence Combiner ◄──────────────────────────────────────────┘
  │  combined = llm * 0.65 + stylometric * 0.35
  │  if |llm - stylometric| > 0.4: pull toward 0.5
  │
  ▼
Attribution + Label Generator
  │  confidence > 0.70  → "likely_ai"     + ⚠️ label
  │  confidence < 0.35  → "likely_human"  + ✓ label
  │  0.35–0.70          → "uncertain"     + ◐ label
  │
  ▼
SQLite Audit Log (audit_log.db)
  │  INSERT row: content_id, creator_id, timestamp,
  │              attribution, confidence, scores, status
  │
  ▼
JSON Response to Client
  { content_id, attribution, confidence,
    signal_scores, label, status }
```

### Appeal Flow

```
Client
  │
  │  POST /appeal
  │  { content_id, creator_reasoning }
  ▼

  ├─── Validate content_id exists in audit_log
  │      404 if not found
  │
  ├─── Update row in SQLite:
  │      status           → "under_review"
  │      appeal_reasoning → creator_reasoning
  │      appeal_timestamp → now (UTC ISO)
  │

  [Human reviewer later reads GET /log to inspect queued appeals]
```

## Detection Signals

### Signal 1 — LLM-Based Classification via Groq

The primary signal uses `llama-3.3-70b-versatile` hosted on Groq to perform semantic-level analysis of the submitted text. The model is prompted to act as a forensic analyst and return a single JSON object containing an `ai_probability` float (0.0 = definitely human, 1.0 = definitely AI) and a short reasoning string.

The LLM captures features that are difficult to encode with heuristics alone, including:

- Absence of personal anecdote, lived experience, or genuine opinion
- Formulaic structure (intro → body → conclusion) without stylistic variation
- Hedged, non-committal phrasing ("it is important to note", "in conclusion")
- Unnaturally consistent paragraph length
- Absence of grammatical idiosyncrasy, colloquialism, or voice

If the model response cannot be parsed as valid JSON, the signal defaults to 0.5 (uncertain) to avoid penalizing the author on a technical failure.

**Weight in final score: 0.65** — the LLM has broader contextual understanding and is the stronger signal for most text types.

### Signal 2 — Stylometric Heuristics (Pure Python)

The secondary signal computes four surface-level linguistic features using only the Python standard library. Together they capture statistical regularities that tend to differ between human and AI writing.

| Metric | Human Range | AI Range | Scoring Formula |
|---|---|---|---|
| Sentence length std dev | > 5 words | < 3 words | `max(0, 1 - std_dev / 8)` |
| Type-token ratio (TTR) | 0.55 – 0.75 | 0.40 – 0.55 | `max(0, 1 - (ttr - 0.3) / 0.5)` |
| Punctuation density | 0.08 – 0.14 | 0.05 – 0.08 | `max(0, 1 - (density - 0.03) / 0.12)` |
| Avg sentence length | Varies widely | Long, uniform | `min(1, avg_len / 25)` |

Each metric produces a score in [0, 1] where higher = more AI-like. The four scores are averaged with equal weights to produce the final stylometric score.

**Weight in final score: 0.35** — heuristics are faster and always available (no API call needed), but are susceptible to false positives from highly technical or formal human writing.

## Uncertainty Representation

Confidence is a single float in [0, 1] representing the estimated probability that the content was AI-generated. The thresholds are:

| Confidence Range | Attribution | Interpretation |
|---|---|---|
| < 0.35 | `likely_human` | Strong evidence of human authorship |
| 0.35 – 0.70 | `uncertain` | Signals are ambiguous or conflicting |
| > 0.70 | `likely_ai` | Strong evidence of AI generation |

The range 0.35–0.70 is intentionally wide. The system is designed to err on the side of acknowledging uncertainty rather than making a confident claim it cannot support. Misclassifying human writing as AI-generated is considered a more serious error than returning "uncertain."

**Disagreement dampening:** When the LLM signal and the stylometric signal differ by more than 0.4, the combined score is pulled 40% toward 0.5. This reduces overconfidence when the two signals conflict, which is a strong indicator that the text falls into an ambiguous category (e.g., highly polished human writing, or AI writing that mimics informal style).

## Transparency Label Design

Three label variants are produced based on the confidence threshold:

**Variant 1 — High-confidence AI (confidence > 0.70)**
> ⚠️ Likely AI-Generated — Our analysis found strong indicators that this content was produced by an AI writing tool. Confidence: {pct}%. The author may appeal this classification if they believe it is incorrect.

**Variant 2 — High-confidence Human (confidence < 0.35)**
> ✓ Likely Human-Written — Our analysis found strong indicators that this content was written by a person. Confidence: {pct}% human. No action required.

**Variant 3 — Uncertain (0.35 ≤ confidence ≤ 0.70)**
> ◐ Attribution Uncertain — Our analysis could not determine with confidence whether this content was written by a person or generated by AI. Confidence: {pct}% AI indicators. Authors may appeal if this label is inaccurate.

The labels are designed with three goals: (1) be honest about the system's confidence, (2) make the appeal pathway visible, and (3) avoid punitive language — the labels describe system findings, not accusations.

## Appeals Workflow

1. A creator receives a label they believe is inaccurate.
2. They call `POST /appeal` with their `content_id` and a `creator_reasoning` string explaining why the label is wrong (e.g., "I wrote this myself, I can provide a draft history").
3. The system updates the submission status from `"classified"` to `"under_review"` and logs the reasoning and timestamp.
4. A human reviewer uses `GET /log` to view all entries, filtering by `status = "under_review"`.
5. The reviewer can examine the `llm_score`, `stylometric_score`, `confidence`, and the `appeal_reasoning` to make a final determination.
6. (Future work) A `PATCH /appeal/{content_id}/resolve` endpoint would allow reviewers to set the final status to `"approved"` or `"upheld"`.

The appeals mechanism ensures the system is not a black box. Creators are guaranteed a human in the loop for any contested decision.

## Anticipated Edge Cases

**Technical / Highly Formal Human Writing**
Academic papers, legal documents, and technical reports often have high TTR and long, uniform sentences. Stylometric scores may lean AI-like even for human-written text. Mitigation: the LLM signal carries higher weight (0.65) and is better positioned to recognize domain-specific formal register.

**Short Texts (< 50 words)**
With too few words, sentence length variance and TTR are statistically unreliable. A single long sentence can dominate the variance calculation. Edge: stylometric scores will be noisy. The system handles this by always falling back to 0.5 for the stylometric signal if the text is too short to produce a meaningful std dev (handled via the statistics module's error handling).

**Mixed Human/AI Text**
A human who pastes AI-generated paragraphs into their own writing will produce a chimeric text. Neither signal is designed for segment-level detection; they analyze the text holistically. This edge case is acknowledged in the label ("could not determine with confidence") and the uncertain band (0.35–0.65) covers many such cases.

**Multilingual or Code-Heavy Text**
The heuristics use English-language assumptions. Code blocks or non-English text will produce unreliable stylometric scores. The LLM signal is more robust to this but may also have reduced accuracy. Both signals may default toward uncertain, which is the appropriate response.

**Rate Limit Abuse**
Flask-Limiter is configured to allow 10 submissions per minute and 100 per day per IP. Users attempting to probe the detection boundary by submitting many variants will be throttled. Distributed attacks from multiple IPs are a known gap; a production deployment would add authentication and per-user limits.

**Groq API Unavailability**
If the Groq API is unreachable or returns an error, the LLM signal defaults to 0.5 and the stylometric signal carries the decision. The final combined score will be pulled toward uncertain. The response still includes `signal_scores` so callers can see that the LLM signal was unavailable.
